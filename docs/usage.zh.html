expctl 中文使用指南

expctl 用 Git 仓库中的请求、回执和结果文件交接异步实验。实验设计者与集群操作者不必同时在线，也能确认运行了哪一版代码、使用了哪些参数，并追溯结果来源。

expctl 支持 SLURM 和在已分配 Linux 计算节点上的直接异步执行。它不替代调度器、工作流引擎或实验跟踪平台；只负责让实验交接可验证、可审计。回执生成后，请求文件不得再修改。

一安装（每台机器一次）

所有机器都需要 Git 和 Python 3.11 或更高版本。local 后端需要带 /proc 的 Linux 环境；SLURM 后端还需要 sbatch、squeue、sacct、scancel，启用节点预算时还会使用 scontrol。推荐使用 uv 安装：

uv tool install git+https://github.com/xfeng01/expctl

更新，以及查看当前安装的版本：

uv tool upgrade expctl
expctl --version

零安装方式：只复制 src/expctl/core.py，运行 python core.py <command>。该文件仅依赖 Python 标准库；Git 和所选后端的系统能力仍须存在。所有命令都应在 Git 工作树内运行。

二初始化项目

在项目仓库中运行：

expctl init

该命令只补齐缺失项，不覆盖已有文件：

expctl.toml                  # 仓库级策略
expctl/
├── requests/               # 实验请求
├── results/                # 回执、日志、指标和报告
└── templates/request.toml  # 请求模板

随后编辑 expctl.toml，确认共享运行时目录和 worktree 位置；使用 SLURM 时还要确认脚本策略和节点上限。

若修改 paths.root，再次运行 expctl init 会在新位置补齐目录，但不会移动或删除旧目录。将配置、请求、模板和结果元数据纳入版本控制；不要提交数据集、模型权重、缓存或密钥。

expctl doctor 分别报告仓库、local 和 SLURM 是否可用。默认只有仓库检查影响退出码；--backend local 或 --backend slurm 会要求对应后端可用。旧的 --cluster 等价于 --backend slurm。

expctl 只读写文件，不会自动执行 git add、git commit 或 git push。

三创建并发布实验请求

  1. 提交并推送本次实验所需的脚本、配置和评测代码。
  2. 从模板创建请求；命令会自动填写 ID、当前 commit、branch 和 worktree 名称： 
    expctl new 20260901-lr-sweep
  3. 编辑生成的请求，填写实验问题、判定规则、输出和指标，并且只保留 [slurm] 或 [local] 其中一种后端，然后验证： 
    expctl validate 20260901-lr-sweep
  4. 将请求文件提交并推送到 Git 仓库。

若工作树存在未提交改动，new 默认拒绝创建，因为这些内容不属于固定的 HEAD。应先提交或暂存；只有明确接受风险时才使用 --allow-dirty。

validate 会检查请求格式、固定提交和脚本。SLURM 脚本必须满足仓库策略；local 脚本必须在固定提交中带可执行位。交互终端会显示后端、commit、脚本、环境变量、日志、指标和依赖摘要。

四提交、查看和收集

每个请求必须且只能选择一种后端。SLURM 使用 [slurm]、script、max_concurrent_nodes 和可选的 [slurm.env]；计算节点直跑使用 [local]、script、可选的 args 和 [local.env]。

local 脚本必须在 Git 中带可执行位；outputs.log_glob 必须是含 {job_id} 的精确路径，不能使用通配符。local 会捕获 stdout/stderr，固定启动节点主机名，并用 Linux /proc 核对 PID 身份；状态、取消和收集必须在同一节点执行。它不提供排队、资源隔离或主机重启恢复。

在执行主机上的项目仓库里：

git pull --ff-only
expctl list
expctl show <id>
expctl submit <id> --dry-run
expctl submit <id>

expctl list 在交互终端中显示对齐表格，管道输出保持稳定 TSV。它批量刷新 SLURM 状态，并从进程身份和退出状态文件刷新 local 状态；刷新只读且不修改回执。可用 --table、--tsv、--json 强制格式。

list 默认按 ID 从新到旧排列；--sort oldest 可反转。--status running,failed 按实时或回执状态筛选。display.list_limit 设置仓库默认显示数量，--limit 20 可临时覆盖，--all 显示全部。没有状态筛选时只处理最终可能显示的 N 个请求；带状态筛选时分批扫描，找到 N 个匹配项后停止；--all 才完整扫描。未配置该字段的旧仓库仍显示所有请求。

面向生命周期的命令在交互终端中使用对齐表格显示详情和建议的下一步；输出到管道或文件时保持 JSON，原始日志除外。需要在终端中获取 JSON 时使用命令支持的 --json。

--dry-run 会验证请求并输出后端、固定提交、worktree 和命令，但不会启动作业。正式提交会创建干净的 detached worktree，检查依赖，再通过所选后端启动并原子完成回执。SLURM 会额外检查资源和节点预算；local 会启动独立进程组并记录 PID、启动标识和退出状态文件。

若需要让请求方立即看到作业号，应在提交成功后单独提交并推送 receipt.json。

看进度

expctl status <id>
expctl status <id> --watch

SLURM 状态使用 squeue 和 sacct；local 状态会核对 PID 与进程启动标识，并在结束后读取退出码。--watch [SECONDS] 默认每 5 秒刷新直到终态。

查看日志与取消

expctl logs <id> --tail 100
expctl logs <id> --follow
expctl cancel <id> --reason "superseded" --dry-run
expctl cancel <id> --reason "superseded"

logs 在运行中读取回执核验的 worktree，收集后读取结果目录。取消时 SLURM 调用 scancel，local 向核验后的进程组发送 SIGTERM；两者都会记录审计信息。取消后的日志仍应收集。

收集结果

expctl collect <id> [--worktree-root <dir>]

collect 会先确认所选后端已经终止，校验请求和 worktree，再暂存并发布日志、提取 metrics.json，最后记录执行终态。

collect 不会等待作业，也不会覆盖已经收集或残留的结果；同一请求的收集过程使用互斥锁串行化。作业仍在队列、没有匹配日志、worktree 不一致、结果已存在或目标文件名冲突时都会报错。

生成并填写报告

expctl report <id>

report 根据请求、回执和 metrics.json 创建 results/<id>/report.md：包含运行事实、原始问题和判定规则、按日志分列的指标表与缺失指标，并留出 Observations 和 Conclusion 供人工填写。已有报告不会被覆盖。报告存在后，list 和 status 显示 reviewed；审阅原始日志并填好结论后，再提交并推送结果目录。

清理 worktree

expctl clean <id> --dry-run
expctl clean <id>

clean 只允许 collected 回执；它重新核对固定提交、仓库归属和工作树内容，并拒绝仍被未收集 rerun 使用的 worktree。结果证据和共享目录的符号链接目标不会被删除。

五请求文件参考

请求必须且只能包含 [slurm] 或 [local] 之一。

字段约束与含义
id形如 20260901-lr-sweep；必须与文件名一致，并匹配 ^[0-9]{8}-[a-z0-9][a-z0-9-]*$
title非空的实验标题
question本实验要消除的不确定性
decision_rule哪种结果会改变下一步决策
code.commit完整的 40 位 Git 提交哈希；这是实际运行的代码版本
code.branch仅供阅读的分支标签，不参与检出或校验
code.worktree实验 worktree 的普通目录名，不能是 . 或 ..，且不得与主仓库重叠
slurm.script固定提交中的仓库相对路径，不得越出仓库
slurm.max_concurrent_nodes允许的最坏并发节点数；固定脚本必须显式声明数字形式的 #SBATCH --nodes，数组范围和 %N 节流也必须可静态解析，推导值不得超过这里的声明
slurm.env传给 sbatch --export 的环境变量；名称须匹配 [A-Za-z_][A-Za-z0-9_]* 且不能是 GROUPS，值必须是字符串且不能包含逗号或换行
local.script固定提交中的仓库相对可执行文件；必须带 Git 可执行位
local.args可选字符串数组，按顺序作为参数，不经过 shell 展开
local.env传给本地进程的环境变量
outputs.log_glob相对于 worktree 且必须包含 {job_id}；SLURM 可使用 glob，local 必须是精确路径
outputs.metrics非空指标名数组；可提取的名称须匹配 [A-Za-z_][A-Za-z0-9_.-]*，对应值必须是独占一行的数字
notes.requirements可选的 worktree 相对路径数组；正式提交前逐项检查是否存在
notes.instructions可选的操作说明；expctl 不解释其内容

支持 name: 1.2、name = 1.2 和 name 1.2 三种完整行。指标名必须完全匹配；单个日志中同名指标出现多次时保留最后一个值，未找到的指标不写入结果。metrics.json 按日志文件分组。

六配置参考

version = 1

[paths]
root = "expctl"

[display]
list_limit = 20

[scheduler]
required_script_lines = ["#SBATCH -p my-partition"]
max_total_nodes = 4

[runtime]
shared_dirs = [".venv", "data", "runs", "logs"]
create_missing = ["runs", "logs"]

[worktree]
root = ".."
  • paths.root：请求、结果和模板的仓库相对目录。
  • display.list_limit：可选，expctl list 默认显示的最大条数；省略时显示全部，--limit 可覆盖，--all 可忽略限制。
  • scheduler.required_script_lines：仅用于 SLURM；必须出现在固定脚本可生效的头部区域。
  • scheduler.max_total_nodes：仅用于 SLURM；当前用户的跨作业节点上限，0 表示禁用检查。
  • runtime.shared_dirs：从主工作树链接到实验 worktree 的顶层目录名。源目录不存在时跳过。
  • runtime.create_missing：提交前可自动创建的共享目录，必须是 shared_dirs 的子集。
  • worktree.root：实验 worktree 的父目录；相对路径以仓库根目录为基准。

节点预算会统计所有占用或正在申请资源的相关状态，并加上请求中的 slurm.max_concurrent_nodes。数组任务使用 squeue -r 展开，因此检查有意偏保守。同一 Git checkout 内的查询—提交窗口会串行化；跨 clone 和人工提交的硬上限仍需 SLURM QOS/account 保证。

--skip-node-check 仅用于 SLURM，会跳过节点预算检查，只应在操作者明确授权后使用。

标准状态：

有效请求，无回执
requested
正在准备或调用执行后端
preparing / submitting
提交结果必须人工对账
submission_unknown
已生成回执；显示后端实时状态
submitted → RUNNING / FAILED / …
已请求后端取消，等待确认
cancel_requested
已执行 collect
collected
已收集且报告存在
reviewed
请求验证失败、仍含模板占位符或回执 JSON 无效
invalid

实时状态还包括 PENDING、COMPLETING、COMPLETED、CANCELLED、TIMEOUT 和 OUT_OF_MEMORY。数组任务有多种状态时显示 MIXED；使用 expctl status <id> 查看逐任务详情。

reviewed 只表示 report.md 已存在，不会写入回执字段；结论仍由操作者填写。

八异常处理与自动化约定

  • 请求在提交作业后被修改：恢复与回执中 request_sha256 完全一致的文件；否则 collect 会拒绝执行。
  • 回执损坏、不可读或缺少有效 worktree：从 Git 或可靠备份恢复并与请求所用后端对账；恢复前，expctl 会保守阻止 worktree 复用和清理。
  • 提交结果不确定：保留 submission_unknown 回执并与后端对账；确认是否存在作业前不得删除回执、重跑或再次提交。
  • SLURM 节点预算不足：等待已有作业释放节点后重试。不要通过修改旧请求或静默重提绕过限制。
  • 作业不再需要：先用 expctl cancel <id> --dry-run 核对作业号，再正式取消；作业离开队列后仍应收集证据。
  • 作业失败、超时或被抢占：保留原回执和日志，在报告中记录失败原因；确认原作业离开队列后用 expctl rerun 创建新 ID，复用的 worktree 必须仍然干净。
  • 日志未找到：核对作业是否结束、outputs.log_glob 是否包含正确的 {job_id} 位置，以及日志是否写在固定 worktree 中。
  • 自动化或 AI 操作：先执行并审阅 --dry-run，再明确授权正式提交。expctl 不会自动重试、重新提交、提交 Git 变更或判定实验结论。
